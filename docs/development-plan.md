# 준스키타운 홈페이지 개발계획서

**프로젝트**: 준스키타운 렌탈샵 홈페이지 (ski-rent-shop)
**작성일**: 2026.07.13
**현재 단계**: M1·M2 완료, M3 백엔드 전환 준비 · [배포 사이트](https://rosookwan.github.io/ski-rent-shop/) · [저장소](https://github.com/rosookwan/ski-rent-shop)

## 1. 개요와 전제

Claude Design 시안(홈 · 공지사항 · 문의게시판 · 셀프견적 · 관리자)을 바닐라 HTML/CSS/JS로 구현한 프로토타입이 GitHub Pages에 배포되어 있다. 현 단계의 목적은 **고객 시연**이며, 데이터는 브라우저 localStorage에 저장된다(방문자 간 공유 안 됨).

**전제 조건**

- 서버(백엔드)는 추후 별도 구축하며, 그 시점에 소스를 이관한다. → 서버 의존 기능은 M3로 미룬다.
- M1–M2는 현재 구조(정적 + localStorage) 안에서 완결되는 개선만 담는다.
- 파일 첨부·이메일 발송·실제 인증은 저장소/서버가 필요하므로 M3 이후에 실동작한다. M1에서는 UI 자리만 마련한다.

**마일스톤 요약**

| 마일스톤 | 내용 | 전제 | 규모 |
|---|---|---|---|
| M1 | 관리자 화면 개편 (게시판형 관리 · 할인 UI) | 없음 — 바로 착수 가능 | M |
| M2 | 사용자 화면 개선 · SEO 기본기 | 없음 | S–M |
| M3 | 백엔드 구축 및 이관 | 서버 인프라 결정 | L |
| M4 | 운영 고도화 | M3 완료 | M |

규모는 상대 추정(S: 며칠 이내 / M: 1주 내외 / L: 2주 이상)이며, 착수 시점에 세분화한다.

## 2. M1 — 관리자 화면 개편

**목표**: 공지·문의가 수십 건으로 늘어도 관리 가능한 게시판형 구조로 전환하고, 할인 설정을 한눈에 읽히게 만든다. 고객 시연에서 "관리 기능"의 완성도를 보여주는 마일스톤.

### 2-1. 공지사항 관리 → 게시판형

현재: 모든 글이 인라인 수정 폼으로 전부 나열 → 글이 많아지면 탐색 불가.

- 목록 화면: 제목 · 태그 · 날짜 컬럼, 행 단위 [수정] [삭제]
- 검색(제목/본문) + 페이지네이션(10건 단위)
- 상단 고정(핀) 기능 — 고정 글은 목록과 사용자 화면 최상단 노출
- 작성/수정은 별도 화면(또는 모달)으로 분리
- 파일·이미지 첨부 UI 자리 마련 (실제 업로드는 M3에서 활성화)

### 2-2. 문의 답변 관리

- 필터 탭: 전체 / 답변대기(N건 뱃지) / 답변완료
- 검색(제목·이름·연락처) + 페이지네이션
- 아코디언 → 상세 화면 전환 (문의 내용 + 견적 첨부 + 답변 에디터)
- 관리자 진입 화면에 요약 카드: "답변대기 문의 N건 · 최근 공지 N건"

### 2-3. 할인 설정 UI 개편

현재: 사용여부/방식/값 버튼이 분산되어 상태 파악이 어렵고, 정액할인 선택 시 품목별 입력칸이 4개 탭에 흩어짐.

- 상단 요약 카드: "현재 적용: 기본 5% · 제휴 12%" 한 줄 요약
- 각 할인을 한 줄로 통합: `[ON/OFF] (퍼센트|정액) [값]`
- 실시간 적용 예시: "종일권 55,000원 → 52,250원"
- 품목별 정액할인 예외를 **할인 탭 안의 단일 테이블**로 통합 (품목 · 가격 · 기본할인 · 제휴할인)

### 2-4. 품목 관리 보완

- 드래그(또는 ↑↓ 버튼) 순서 변경 — 셀프견적 노출 순서 반영
- 품절/숨김 토글 — 셀프견적에서 임시 제외
- 가격 입력 천단위 콤마 표시

### 2-5. 내부 정리

- 기본 데이터(품목·공지·문의)가 `site.js`/`admin.js`에 중복 정의 → `site.js`로 단일화

**완료 기준**: 공지 30건·문의 30건을 넣은 상태에서 검색·필터·페이지네이션으로 10초 내 특정 글을 찾을 수 있다. 할인 상태가 요약 카드 한 줄로 읽힌다.

## 3. M2 — 사용자 화면 개선 · SEO 기본기

**목표**: 손님이 보는 화면의 완성도와 공유·검색 노출 품질을 올린다.

### 3-1. 게시판

- 공지사항: 페이지네이션(더보기 → 페이지 방식), 고정 공지 상단 표시, 첨부파일 표시 영역
- 문의게시판: 비밀글 열람 시 비밀번호 확인 플로우 완성(작성 시 저장한 비밀번호 대조), 작성자 마스킹 표시(홍*동), 페이지네이션

### 3-2. 셀프견적

- 담은 내역 로컬 저장 → 재방문 시 "이어서 하기"
- 가격은 손님에게 노출하지 않고 문의 등록 후 안내하는 현행 정책 유지

### 3-3. SEO·공유 기본기

- favicon, OG 태그(카카오톡/SNS 공유 미리보기 이미지·제목), 페이지별 meta description
- sitemap.xml, robots.txt
- 가게 정보 구조화 데이터(JSON-LD: 상호·주소·전화·영업시간) — 검색/지도 노출 대비

**완료 기준**: 카톡에 링크 공유 시 상호·설명·이미지가 미리보기로 뜬다. 비밀글이 비밀번호 없이는 열리지 않는다.

## 4. M3 — 백엔드 구축 및 이관

**목표**: 데이터를 서버로 옮겨 "손님이 등록한 문의가 사장님 관리자에 실제로 보이는" 실서비스 구조로 전환한다. 상세 구현·검수 기준은 [M3 요구사항](requirements/M3-backend-migration.md)을 따른다.

### 4-1. 인프라 결정 (착수 전 협의)

| 선택지 | 장점 | 고려사항 |
|---|---|---|
| BaaS (Supabase 등) | DB+인증+파일저장 일체, 무료 티어, 서버 운영 부담 없음 | 서비스 종속 |
| 자체 서버 (Node/Spring 등) | 완전한 통제, 기존 인프라 활용 | 구축·운영 비용, 보안 직접 관리 |

**결정(2026.07.13)**: 기존 Vultr 서버를 RAM 2 GB·SSD 55 GB 플랜으로 확장해 사용한다.
FastAPI와 SQLite로 시작하고, 준스키타운 전용 사용자·systemd 서비스·Nginx 설정으로 기존
테니스 서비스와 분리한다. 실서비스 도메인은 최종 배포 단계에서 확정한다.

### 4-2. 작업 항목

- DB 스키마 구축 (§7 초안 참조) 및 기본 데이터 시딩
- 관리자 인증: 실제 계정/비밀번호, 세션 관리 (현재는 아무 값이나 통과)
- 파일 스토리지 연동 → M1에서 자리만 만든 첨부 기능 실동작
- 프론트 연동 교체: localStorage 읽기/쓰기 → API 호출 (페이지 구조는 유지)
- 비밀글 비밀번호 해시 저장, 관리자 페이지 접근 제어
- 배포 구성: 프론트(정적 호스팅 유지 가능) + API 서버, 도메인 연결

**완료 기준**: 손님 폰에서 등록한 문의가 사장님 PC 관리자 화면에 보인다. 관리자 로그인이 실제 계정으로만 된다. 공지에 이미지를 첨부해 게시할 수 있다.

## 5. M4 — 운영 고도화

**목표**: 실서비스 운영 편의 기능. M3 완료 후.

- 셀프견적 이메일 실발송 (현재는 시뮬레이션)
- 문의 등록 시 관리자 알림 (이메일 또는 카카오 알림톡)
- 공지 노출 기간 설정(자동 게시/내림), 임시저장
- 관리자 대시보드 통계: 기간별 문의 수, 견적에 많이 담긴 품목
- 견적 URL 공유 (링크로 견적 내역 전달)
- 데이터 백업 정책

## 6. 결정 현황

마일스톤 착수·배포 전에 확인할 정책과 현재 결정 상태.

1. **가격 노출 정책** — 금액 비노출, 문의 후 안내로 확정
2. **비밀글 범위** — 기본 체크 유지, 작성자 비밀번호 또는 관리자 인증으로만 열람
3. **인프라 선택** — 자체 Vultr 서버로 확정 (FastAPI + SQLite)
4. **도메인** — R14 실서비스 배포 전 확보 및 연결

| admins | id, login_id, password_hash | (신규 — 현재 인증 없음) |

## 8. 리스크

- **localStorage 한계에 대한 고객 오해**: 시연 시 "지금은 기기별 저장, 서버 전환(M3) 후 공유됨"을 명시해 기대치를 맞출 것
- **첨부 UI 선노출**: M1에서 첨부 자리만 있고 동작하지 않으므로, 시연 시 "서버 연동 후 활성화" 라벨 표시
- **이관 시점의 데이터**: 프로토타입 기간에 실제 문의가 쌓이면 M3에서 마이그레이션 필요 — 시연 데이터와 실데이터 구분 운영 권장
