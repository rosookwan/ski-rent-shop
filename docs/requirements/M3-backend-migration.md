# M3 요구사항 — 백엔드 구축 및 실서비스 이관

대상: `backend/`, `js/store.js`, 데이터 호출 페이지, 서버 배포 설정
배경: [개발계획서 §4](../development-plan.md) · 구조: [architecture.md](../architecture.md) ·
공통 규칙: [AGENTS.md](../../AGENTS.md)

## 확정된 기술 구성

- 인프라: 기존 Vultr `tennis-notification-bot` 서버에 별도 서비스로 배포
- 서버 사양: 1 vCPU, RAM 2 GB, SSD 55 GB
- 백엔드: Python FastAPI + Uvicorn
- 데이터베이스: SQLite로 시작하고 데이터 접근 계층을 분리해 향후 PostgreSQL 전환 가능하게 구성
- 파일: 서버 로컬 전용 디렉터리에 저장하고 DB에는 메타데이터와 상대 경로만 저장
- 프론트: 기존 루트 HTML·바닐라 JS·페이지 URL을 유지하고 `JSTStore` 구현만 API 방식으로 전환
- 서버 분리: 전용 리눅스 사용자, Python 가상환경, systemd 서비스, Nginx 설정 사용
- 실서비스 도메인은 R14 배포 시점에 확정한다.

## 공통 보안·데이터 원칙

1. 비밀번호와 세션 토큰을 평문으로 저장하거나 로그에 남기지 않는다.
2. 관리자 API와 파일 변경 API는 인증 없이는 처리하지 않는다.
3. 사용자 입력은 서버에서 길이·형식·허용값을 다시 검증한다. 프론트 검증만 신뢰하지 않는다.
4. SQL은 매개변수 바인딩으로 실행하고 파일 경로는 서버가 생성한다.
5. 실제 개인정보를 받기 전 HTTPS, 관리자 인증, 백업을 모두 적용한다.
6. `.env`, DB, 업로드 파일, 인증 비밀값을 Git에 커밋하지 않는다.
7. 기존 `jst_trip_info`, `jst_estimate`, `jst_estimate_draft`는 브라우저 내부 전달 데이터이므로
   localStorage에 유지한다.

## R9. 백엔드 기반과 DB 초기화

### 요구사항

1. `backend/`에 FastAPI 애플리케이션 구조를 추가한다.
2. `GET /api/health`는 DB 연결 여부와 함께 `200` JSON을 반환한다.
3. 환경변수로 DB 경로, 업로드 경로, 허용 Origin을 설정하고 `.env.example`에 이름만 문서화한다.
4. SQLite 연결 시 foreign key, busy timeout, WAL 모드를 활성화한다.
5. 앱 시작 시 버전이 기록된 마이그레이션을 순서대로 적용한다. 이미 적용된 마이그레이션은
   다시 실행해도 데이터를 손상하지 않아야 한다.
6. 다음 테이블의 기반 스키마를 만든다.
   - `notices`, `notice_files`
   - `inquiries`
   - `catalog_items`, `discount_config`
   - `admins`, `admin_sessions`
   - `schema_migrations`
7. 개발 실행·테스트 명령과 디렉터리 구조를 `backend/README.md`에 기록한다.
8. Python 의존성은 버전을 고정한다. 프론트에는 빌드 도구나 npm 의존성을 추가하지 않는다.

### 완료 기준

- 새 임시 DB에서 서버를 실행하면 전체 테이블과 마이그레이션 버전이 생성된다.
- 같은 DB로 두 번 실행해도 오류나 중복 데이터가 없다.
- `GET /api/health`가 정상 DB에서는 `200`, DB 연결 실패 시에는 성공으로 위장하지 않는다.
- 백엔드 자동 테스트와 기존 `node --check js/*.js`가 통과한다.

## R10. 공용 데이터 API와 초기 데이터

### 요구사항

1. 현재 `JSTStore` 스키마와 호환되는 응답 변환 계층을 둔다. DB 컬럼명을 UI 전체에 직접 노출하지 않는다.
2. 사용자 화면에 필요한 읽기 API를 구현한다.
   - 공개 공지 목록·상세: 고정 우선, 최신순, 페이지네이션
   - 노출 품목 목록: 카테고리·정렬순서 반영, 숨김 품목 제외
   - 활성 할인 설정
3. 문의 등록 API를 구현한다.
   - 이름·연락처·제목·내용·비밀글 비밀번호·견적 JSON 검증
   - 비밀글 비밀번호는 안전한 단방향 해시로 저장
   - 서버가 작성일·상태·ID를 부여
4. 공개 문의 목록은 관리자 답변 상태와 마스킹된 작성자만 노출한다. 연락처·이메일·비밀번호 해시·
   비밀글 본문은 목록 응답에 포함하지 않는다.
5. 비밀글 상세는 비밀번호 검증 API를 통과한 경우에만 반환한다.
6. 기존 기본 품목·공지·할인 설정을 빈 DB에 한 번만 시딩한다.
7. 모든 목록 API에 서버 측 최대 페이지 크기를 둔다.

### 완료 기준

- 서로 다른 브라우저에서 동일한 공지·품목 데이터를 조회한다.
- 브라우저 A에서 등록한 문의가 DB에 저장되고 비밀번호 원문은 DB에서 확인되지 않는다.
- 비밀글은 빈 비밀번호와 오답으로 열리지 않고 정답으로만 열린다.
- 빈 DB 시딩을 반복해도 중복 품목·공지가 생성되지 않는다.

## R11. 관리자 인증과 관리 API

### 요구사항

1. 기본 관리자 계정을 코드나 시드에 넣지 않고 CLI 명령으로 생성·비밀번호 변경한다.
2. 비밀번호는 단방향 해시로 저장하고 로그인 성공 시 예측 불가능한 세션 토큰을 발급한다.
3. 세션은 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키를 사용하고 서버 DB에는 토큰 원문 대신
   해시와 만료 시각을 저장한다.
4. 로그인·로그아웃·현재 세션 확인 API를 구현한다. 실패 응답으로 계정 존재 여부를 구분할 수 없게 한다.
5. 반복 로그인 실패에 IP와 계정 기준의 제한을 적용한다.
6. 관리자 전용 API를 구현한다.
   - 공지 작성·수정·삭제·고정·검색·페이지네이션
   - 문의 원문·견적 조회, 답변 저장, 상태 변경, 검색·필터·페이지네이션
   - 품목 작성·수정·순서·숨김 관리
   - 할인 설정 저장
7. 모든 변경 요청에서 허용 Origin을 확인하고 인증되지 않은 요청은 `401` 또는 `403`으로 거절한다.

### 완료 기준

- 잘못된 로그인, 만료 세션, 로그아웃된 세션으로 관리자 API를 사용할 수 없다.
- 정상 로그인 후 기존 관리자 화면에 필요한 CRUD를 모두 API로 수행할 수 있다.
- 브라우저를 새로 열어도 유효한 세션이면 로그인 상태가 유지되고 만료 후에는 로그인 화면으로 이동한다.
- 관리자 비밀번호·세션 토큰 원문이 DB와 애플리케이션 로그에 남지 않는다.

## R12. 공지 첨부파일 실동작

### 요구사항

1. M1·M2에서 비활성으로 만든 공지 첨부 UI를 실제 업로드·목록·삭제 기능으로 전환한다.
2. 업로드는 관리자 인증이 필요하며 파일 개수, 개별 크기, 전체 크기, 허용 확장자와 MIME을 제한한다.
3. 저장 파일명은 서버가 UUID로 생성하고 원본 파일명은 표시용 메타데이터로만 보관한다.
4. 업로드 디렉터리 밖의 파일을 읽거나 삭제할 수 없도록 경로를 검증한다.
5. 공개 공지 상세에서는 첨부파일 이름·크기·다운로드 링크를 표시한다.
6. 공지 삭제 시 첨부 메타데이터와 실제 파일을 일관되게 정리한다. 실패 시 고아 파일을 점검할 수 있는
   관리 명령을 제공한다.

### 완료 기준

- 관리자가 허용 파일을 올린 공지를 저장하면 다른 브라우저에서도 다운로드할 수 있다.
- 비로그인 업로드, 제한 초과 파일, 실행 파일, 경로 조작 파일명이 거절된다.
- 첨부 삭제 및 공지 삭제 후 해당 파일을 URL로 다시 받을 수 없다.

## R13. 프론트 JSTStore API 전환

### 요구사항

1. `js/store.js`에서 서버 공유 대상 데이터만 API로 읽고 쓴다.
   - 서버 대상: 공지, 문의, 품목, 할인, 관리자 인증, 공지 첨부
   - 브라우저 유지: 홈 일정 전달, 견적 전달, 견적 임시저장
2. API 주소는 `js/config.js` 한 곳에서 관리하며 개발·운영 주소를 구분할 수 있어야 한다.
3. API 호출 함수는 Promise를 반환하고 페이지 초기화·저장 액션을 `async` 흐름으로 조정한다.
4. 로딩·빈 상태·네트워크 오류·인증 만료 상태를 한국어 UI로 표시한다.
5. 문의 등록 중 중복 클릭을 막고 서버 성공 응답을 받은 뒤에만 견적 임시저장을 삭제한다.
6. 관리자 로그인은 실제 인증 API를 사용하며 기존 `jst_admin_session` 우회 로직을 제거한다.
7. 사용자 입력 렌더링 시 기존 `esc()` 적용을 유지한다.
8. 프로토타입 localStorage 공유 데이터는 자동으로 서버에 올리지 않는다. 초기 데이터는 R10 시드로 관리한다.

### 완료 기준

- 손님 브라우저에서 등록한 문의가 새로고침 없이 또는 관리자 재조회 후 사장님 브라우저에 표시된다.
- 관리자 로그인은 등록된 계정·비밀번호로만 성공한다.
- 공지·품목·할인 변경이 다른 브라우저의 사용자 화면에 반영된다.
- API 중단 시 무한 로딩이나 콘솔 미처리 예외 없이 복구 안내가 표시된다.
- 홈 → 셀프견적 → 문의 등록 핵심 흐름과 모바일·데스크톱 검증을 통과한다.

## R14. 서버 배포·HTTPS·백업·운영 전환

### 요구사항

1. Vultr 서버에 준스키타운 전용 리눅스 사용자와 배포 디렉터리를 사용한다. 테니스 웹과 봇의 사용자,
   서비스, 데이터 디렉터리를 공유하지 않는다.
2. 전용 Python 가상환경과 systemd 서비스를 만들고 자동 재시작·로그 정책을 설정한다.
3. Nginx에서 선택한 도메인의 정적 파일과 `/api`를 연결하고 HTTPS 인증서를 적용한다.
4. 운영 CORS·쿠키·Origin 설정은 확정 도메인만 허용한다.
5. 방화벽에서 외부 공개 포트는 필요한 HTTP(S)만 추가하고 백엔드 포트는 로컬에서만 접근 가능하게 한다.
6. SQLite DB와 업로드 디렉터리를 일관된 시점으로 백업하고 복원하는 스크립트와 주기를 만든다.
   Vultr 자동 백업만을 애플리케이션 백업의 유일한 수단으로 사용하지 않는다.
7. 배포 전 기존 서버 메모리·디스크를 기록하고 배포 후 서비스별 사용량과 실패 서비스를 비교한다.
8. 장애 시 이전 버전으로 되돌리는 배포 절차와 DB 마이그레이션 복구 절차를 문서화한다.

### 완료 기준

- HTTPS 도메인에서 사용자 화면과 API가 정상 동작하고 HTTP는 HTTPS로 이동한다.
- 서버 재부팅 후 준스키타운과 기존 테니스 서비스가 모두 자동으로 복구된다.
- 백업본으로 별도 임시 위치에 DB와 첨부파일을 복원하는 테스트가 성공한다.
- 브라우저 콘솔 오류 0건, 핵심 문의 흐름, 관리자 인증·답변·첨부 흐름을 실제 서로 다른 브라우저에서 통과한다.
- 배포 후 실패한 systemd 서비스가 없고 메모리·디스크 여유가 운영 기준을 충족한다.

## 구현 순서

`R9 → R10 → R11 → R12 → R13 → R14`

- R9~R12는 로컬에서 API와 자동 테스트를 완성한다.
- R13에서 기존 프론트를 API에 연결한다.
- R14 직전에 실서비스 도메인과 관리자 계정 정보를 확정한다.
- 각 R은 완료 기준을 검증한 뒤 별도 커밋한다.
